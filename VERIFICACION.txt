14) SEGURIDAD: LA CLAVE PÚBLICA YA NO PUEDE BORRAR  (sql/007_permisos.sql)
   Problema (comprobado en una base real): toda función nueva en Postgres
   recibe EXECUTE para PUBLIC. En Supabase el esquema public está expuesto por
   la API REST y la clave `anon` es PÚBLICA (viaja en el addon de Stremio).
   Con esa clave se podía hacer, literalmente:
     POST /rest/v1/rpc/purge_junk_torrents   {"p_dry_run": false}   -> borra
     POST /rest/v1/rpc/renumber_torrent_ids  {"p_start": 500}       -> 1..9 -> 500..507
   Arreglo:
     · revoke de las 23 funciones a PUBLIC / anon / authenticated
     · grant solo a service_role (GitHub Secrets) y a postgres
     · public.torrents_security_audit() para vigilarlo (la usa `doctor`): revisa
       permisos de las funciones, permisos de la tabla, POLÍTICAS RLS que dejen
       escribir a la clave pública y si RLS está desactivado
     · el job de pruebas del workflow crea los roles ANTES de aplicar el SQL y
       verifica al final que anon/authenticated no pueden ejecutar nada
   Verificado: como anon -> "permission denied"; como service_role -> funciona.

15) NADA SE BORRA SIN PERMISO EXPLÍCITO + TÍTULO EFECTIVO
   · Filas SIN ningún nombre (title y title_text vacíos): se CONSERVAN. Solo se
     borran si pones PURGE_EMPTY_TITLE=true (p_purge_empty en el RPC).
     Motivo: un borrado no se puede deshacer y esas filas no estorban.
   · El nombre del release se busca en `title` y, si está vacío, en `title_text`
     (título efectivo) en las 4 funciones que agrupan/borran por nombre
     (purge_junk, purge_blocked, keep_best_torrents, keep_best_torrents_es).
     Antes: con `title` vacío en toda la tabla, todas las filas compartían la
     clave 'title:', se agrupaban como UNA sola obra y la regla de español
     borraba todo menos 3 (probado: 8 filas -> 1 grupo).
   · Las filas sin título ni ningún id NO se agrupan nunca (se cuentan como
     "skipped").
   · El reordenador toma `lock table public.torrents in access exclusive mode`
     (con lock_timeout 15s): un INSERT de la app ya no puede chocar con un id a
     medio asignar. Si hay una transacción larga, aborta con error claro y sin
     haber tocado nada.

17) EL BUG MÁS PELIGROSO DE TODOS: UN ID MAL PUESTO BORRABA TORRENTS LEGÍTIMOS
   (encontrado con un escenario de 1.000 filas + pipeline completo)
   Cadena del fallo:
     a) el enriquecedor prueba variantes del título cuando no hay match: "Obra 2" -> "Obra"
     b) existe una película que se llama literalmente "Obra"  ->  match PERFECTO (1.0) y
        confianza 0.95  ->  el MISMO imdb_id se escribía en cientos de filas distintas
     c) la limpieza agrupa por imdb_id -> las ve como "la misma obra" -> conserva el top 3 y
        borra el resto.  Resultado medido: 402 filas borradas de 1.000 (de 300 obras, 53
        familias perdieron filas) y la caché "inventaba" 0.95 al reutilizar un acierto, así
        que el id dudoso parecía bueno.
   Arreglos (los tres):
     1) PENALIZACION_VARIANTE = 0.8: un match conseguido con una variante sintética del
        título vale menos (0.95*0.8 = 0.76). Aplica a IMDb suggestions y a TVmaze.
     2) La caché (local y persistente) guarda y devuelve la confianza REAL; si no la tiene,
        devuelve 0.5 ("desconocida") en vez de inventar 0.95.
     3) Las funciones que borran solo agrupan por id si el id es de fiar:
        torrent_id_es_confiable(ids_source, ids_confidence) = id que ya venía en la tabla
        (ids_source null) o escrito por nosotros con confianza >= 0.92. Si no, agrupan por
        TÍTULO (mucho más conservador). También las salvaguardas de "fila sin título ni id".
   Antes/después con el MISMO escenario (1.000 filas, top 3):
     antes -> 402 borradas (598 quedan), familias destrozadas
     ahora ->  11 borradas (989 quedan), 231 familias intactas con sus 3 filas
   Regresión en el smoke ([14]): 10 obras distintas con el mismo id a 0.89 -> 0 borrados;
   el mismo id a 0.99 -> agrupa y deja el top 3; id propio (sin ids_source) -> se respeta.
